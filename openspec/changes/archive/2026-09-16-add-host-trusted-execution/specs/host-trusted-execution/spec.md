## ADDED Requirements

### Requirement: Standalone prototype build preparation

Stage one SHALL provide unshipped, non-production Windows launcher source and explicit build tooling without enabling host-trusted or altering Linux bwrap. The launcher source SHALL express suspended creation, successful Job assignment before resume, bounded control/termination and distinct lifecycle observations. Local acceptance SHALL test build planning, request validation and intended source contract without claiming native lifecycle qualification. Compilation SHALL occur only in an explicit native build step, never at package runtime or import.

#### Scenario: Build contract is testable without native execution

- **WHEN** local preparation tests exercise request validation and compiler/build planning with controlled adapters
- **THEN** unsafe paths/arguments, mounts, malformed environment and unsupported inputs are rejected, supported plans are shell-free and import has no launch side effects
- **AND** source-contract checks are labelled preparation evidence rather than Windows containment proof

#### Scenario: Explicit build binds native outputs

- **WHEN** the build CLI is invoked with a selected output directory
- **THEN** wrong platform/architecture or missing compiler fails without download or fallback, and a successful actual Windows build binds source, recipe, toolchain, architecture and helper hashes in its output manifest
- **AND** a native binary is generated by the build step, not model-authored text or Base64 candidate transport

### Requirement: Qualification harness preparation

Stage one SHALL supply a macOS managed-process-group prototype, bounded lifecycle fixtures and a native qualification CLI with locally testable planning and result validation. The CLI SHALL require actual native capabilities and successful actual test execution before writing a qualified result. Injected unit observations SHALL NOT be admitted as native proof. Root exit, declared-scope descendant settlement and uncertain termination SHALL remain distinct. Infrastructure failure SHALL NOT count as expected-red. macOS active detachment and arbitrary daemon descendants SHALL remain outside the advertised prototype guarantee.

#### Scenario: Harness rejects misleading observations

- **WHEN** local tests supply root-only exit, malformed/incomplete cases, timeout, launch failure or unconfirmed termination observations
- **THEN** result validation rejects qualification, records the appropriate failure or uncertainty and never treats witness text as an infrastructure failure becoming product Red
- **AND** fake adapters test only preparation behavior and cannot create a CLI native-qualified report

#### Scenario: Native entrypoint fails closed until actually qualified

- **WHEN** an operator invokes the native qualification CLI on a wrong platform or with missing/tampered helper or incomplete lifecycle results
- **THEN** it fails nonzero without skip, download, runtime compilation or a success manifest
- **AND** actual successful native cases alone produce source/helper/platform/architecture/Node-bound qualification output, with bounded logs and no environment credential values

### Requirement: Staged CI and support boundary

Stage one SHALL add ordinary native prototype CI entries for Windows x64 and macOS x64/arm64 on Node 22.13.0 and 24.13.0, plus build/test handoff documentation. CI configuration and local contract tests SHALL establish preparation only, not execution evidence. Missing native results SHALL block dependent later integration but SHALL NOT block local preparation acceptance. Existing production modes, generated files, package membership, storage recovery and Linux real isolation regression SHALL remain unchanged.

#### Scenario: Native CI is explicit and preserves existing coverage

- **WHEN** the prepared CI workflow is inspected by local contract tests or later executed on a matching native runner
- **THEN** each declared lane asserts actual architecture and Node, explicitly builds/tests the prototype, preserves failing status and retains identity-bound diagnostics/artifacts without secrets or automatic publishing
- **AND** existing OpenSpec, storage and real Linux bwrap jobs remain intact, while merely passing configuration tests is not reported as a native result

#### Scenario: Preparation delivery does not enable host support

- **WHEN** preparation is compiled, tested and delivered without real native qualification
- **THEN** documentation reports prototype preparation complete and native qualification pending, production continues admitting only its existing execution modes, prototype scripts remain outside the distributed package, and later host integration still requires actual native qualification and full workflow acceptance
