## 2. Durable history: useful code is not yet the required storage contract

1. **Existing Cadence does not capture these details.** `src/sdk-worker.mjs:315-402` emits ready, tool name and final text; richer SDK events are inspected but not published.
   `src/task-store.ts:324-350` refuses task-directory siblings other than `task.json`.
   Rich history needs deliberate worker protocol/capture and separately versioned storage, not frontend polling or adding JSONL next to old records.
   Existing `.trellis/spec/frontend/state-management.md` keeps history, authority, checks and human review separate; the new product must revise maintained contracts after approval, not bypass them.
2. **Upstream truncates before rendering.** `U:server/serialize.ts:15-33,98-102,170-193` caps assistant text at 200,000 characters, tool output at 100,000 and arguments at 20,000; structured tool details can be dropped above 64,000.
   `U:web/src/components/FilePreview.tsx:31-32,709-719` caps rendered file lines at 5,000.
   Reusing these preview caps is compatible only with explicit completeness flags and a route to retained detail; a short preview cannot be relabeled a complete archive.
3. **Search is bounded and narrower than “all history.”**
   Normal history discovery selects at most 200 current-workspace sessions (`U:server/agent-service.ts:10840-10907`); search returns 50 hits (`:12668-12703`).
   Search text is capped at 256 Ki characters (`U:server/session-search.ts:23-29`; `U:server/session-parser.ts:209-245`); anchors scan at most 16 MiB and return ten hits, user/assistant only (`U:server/session-search.ts:59-90`).
   The parser's text-collection branch does not enforce that same role filter, despite comments claiming aligned scope: tool-result matches can lack anchors.
   Preserve UI/query mechanics, replace these semantics with paged coverage-aware search over agreed retained fields, including tool details if approved.
4. **Readonly parsing is reusable, not lossless storage.** `U:server/conversation-read-tool.ts:223-291` truncates per-message/global formatted text and skips malformed JSONL lines; it does not preserve all entry/call identities.
   `U:server/tool-host-factories.ts:133-152` scans listed Pi history and synchronously reads a size-bounded file.
   Reuse/adapt these read algorithms, not ambient global import or a silent “no records” response on corruption.
   Compaction recovery separates display history from model context (`U:server/compacted-history.ts:134-194`); its serializer still needs replacing if it would save image attachments while merely viewing.
5. **A deep link is navigation, not permission.** `U:web/src/session-url.ts:44-52` strips `?token=` when copying valid URLs; `:89-103` falls back to timestamp-prefix message matching.
   Use stable persisted Cadence IDs and report missing anchors, not guessed matches.
   Token-link entry is separately selected auth; history exports/deep links must not carry the owner secret.
6. **Export is a genuine integration gap, not deferred scope.**
   Upstream message Markdown/text copy and selected-message PNG are reusable UX, but omit task graph, action receipts, closure, checks and human review.
   Once agreed, a complete export must enumerate the selected parent/child episode(s), include accessible retained detail and provenance/omissions, and work beyond the loaded DOM or recent event ring.
   Never claim a screenshot is a complete recorded-history export.

## 4. Thin adapters and genuinely new integration work

- **Presentation projection:** one service DTO adapter supplies task/run/assignment identity, graph, lifecycle/outcome/closure, checks, review, message/tool/artifact IDs and recording coverage.
  Renderers may select/fold/filter locally but never derive execution truth.
  Adapt upstream type shims rather than drag its several-thousand-line general chat/admin protocol into the service.
- **Control gateway:** replace `appSend`/`panelSend` calls with an explicit allowed action interface: task creation/plan edits, fresh Start, Cancel request, confirmed real parent check, human review.
  Server binds context/version/action ID and returns durable receipts; a hidden button or client `readOnly` prop is not authorization.
  No prompt-as-Start, replay-on-reconnect or imported retries.
- **History repository:** bounded pages for list/search/messages/tool detail/events/artifacts/export over newly owned records, independently readable without SDK/model construction.
  Separate a small realtime buffer from durable history; old records without captured detail say “unavailable,” never inferred transcripts.
  UI demand controls lazy retrieval, not whether an unattended run gets recorded.
  Stable IDs preserve tool associations across page boundaries; orphan results must remain inspectable, unlike MessageList's unconditional top-level tool-result suppression (`U:web/src/components/MessageList.tsx:1180-1182`).
- **Timeline bridge:** implement the small mount/context interface already used by `entry.mjs`; adapt payload/status types and remove unrestricted `clear`/CDN calls.
  No need to install upstream plugin discovery, loaders or `PluginManager` just to reuse a ~1,500-line visualization.
- **Privacy/resource contract:** separate retained approved content from public previews, provider secrets and private diagnostics.
  Define redaction/omission markers, authenticated detail/download paths, byte/page/queue/disk quotas and crash-tail semantics.
  Quotas must not silently evict agreed recorded history; refuse/pause safely or follow an explicitly selected retention policy.
  Full recorded history means inspectable retained content and honest gaps, **not unlimited raw capture, hidden provider data or every file on the host**.
- **New functionality that UI reuse cannot supply:** shared independent owner/admission/scheduler, versioned capture/durability, complete history search/export, Cadence-specific check/review controls and cross-client authority.
  These belong in this same integrated delivery.
  Significant existing UI reuse reduces duplicated rendering/interaction work, not the need for these contracts.

## 5. Recommended completeness boundary and user-owned details

Recommend one task workspace containing: creation and readable decomposition/plan; both independent operational clients; bounded dependency/status visibility; each agent's conversation and input/output inspection; shared live timeline; durable browse/search/export of the agreed recorded task history; actual checks/change inspection/human closure; remote owner-token access; existing Pi model auth; service operations/docs and packaged qualification.
None is proposed as a later product release.

The consolidated review still owns **which content is recorded/exportable**: normal prompts/replies and tool args/results versus provider-emitted reasoning, binary/media attachments and historical file/diff bodies; how redaction/sensitive content is treated; searchable fields and task/workspace scope; export format/scope; retention/deletion policy and acceptable resource ceilings.
Recommend paged ordinary messages/tool details with explicit omissions, not a summary-only compromise.
Do not silently choose reasoning capture, unlimited transcript retention or credential-bearing raw export.
Technical page sizes/index choice can be design decisions after those product boundaries converge.

Not required by “complete Cadence workspace”: arbitrary browser shell/PTY, SCM mutation/commit UI, general chat replacement, plugin marketplace/dynamic execution, Electron/desktop packaging, SSH/DSH engine parity, accounts/multi-user hosting, automatic continuation or old-history migration.
Excluding these does not defer agreed task functionality.

## 6. Integrated acceptance scenario — proposed, not executed

1. Install the actual packed package in an isolated qualification environment; configure the independent service, selected Pi credential store and explicit secure remote route.
   Demonstrate ordinary terminal-only create → plan → fresh Start → actual check → change inspection → human review with no browser.
   Starting the service/viewing history alone starts no task.
2. With no Pi terminal alive, enter the WebUI on another computer/phone via owner token; create/review a decomposed task, then explicitly Start.
   Two readonly children really overlap; competing editing assignments across tasks serialize in one checkout.
   Browser and subsequently attached terminal show the same identities, admission/wait reasons and outcomes.
3. Inspect each child's conversation, tool input and output, long paged detail and shared timeline.
   Close initiating clients while work continues; reopen another tab/device.
   Force a missing delta/final snapshot and stale/duplicate Start requests: resync converges, no duplicate launch, no silent success from connection state.
   Recorded content does not depend on a viewer being present.
4. Run failure/cancellation branches: one child fails, parent Cancel stops admission and requests bounded active-child cancellation, and a fixture with unconfirmed closure remains unknown/fenced.
   All child results, blocked dependencies and partial work remain inspectable; no all-green aggregate masks them.
5. Explicitly confirm actual parent checks, inspect changes (including pre-existing dirt and coverage limits), then record human review.
   Failed/unrun/stale checks remain such after acknowledgment; agent review never becomes human approval.
6. Restart the service, browse/search/export completed and interrupted episodes without runtime creation/repair/replay.
   Find a known tool-output/message hit beyond the initial list/page/realtime buffer, open its exact anchor, retrieve retained long detail, and export it with child links/checks/review plus omission/provenance metadata.
   Test quota/corruption and missing legacy-detail states without changing old bytes or synthetic tool completion.
7. Verify unauthorized/cross-origin HTTP/WS/detail/export refusal, cookie-first navigation/reconnect, token rotation, secret-free projections and no credential material in exports.
   Fake-provider qualification covers SDK-coordinated refresh/writeback and preserved unrelated entries; distinguish that executed test from any unexecuted real-provider qualification.
8. Complete both-client phone/desktop controls, package assets/notices, service docs and full integration evidence before closing the parent.
   Static mocks, one backend module or screenshot export alone cannot satisfy this scenario.
