# Abel 授权、计划与恢复协议重构方案

状态：总体架构建议；当前已实现防循环、Implement 默认由父模型推荐决策、技术暂停原地修订与有限自动继续。
完整结构化 ChangeContract、执行器内置通用 DAG 拆分和环境自举仍属于后续演进。
最新交互原则：Design 完成主要决策，Implement 的新增实施选择由父模型采用推荐方案后继续，不再默认要求用户增量回答。
下文早期分析描述的是重构前问题；实现范围以增量设计文档为准。
当前实现与验证范围见 `openspec/changes/reduce-workflow-approval-loops/design.md`。
分析对象：当前工作区，包括尚未提交的 `reduce-workflow-approval-loops` 改动。
本方案取代该改动中“精确计划代表用户授权、恢复上下文变化即可重新计数”的长期设计；现有改动仍保留，本文不修改产品代码或现行规范。

## 1. 判断与目标

当前项目仍可能反复进入审批等待，也仍有无进展恢复循环。
根因是三种本应独立的事实被耦合：用户允许什么、系统准备怎样做、一次执行具体允许访问什么。
执行计划不可能在探索阶段穷尽所有辅助文件、验证准备和修复路径；把计划细节全部变成授权边界，会让正常实现不断制造“缺少授权”。

建议以一个持续的 change 为中心，建立稳定的授权契约、可修订的执行计划和每次执行的精确能力。
用户负责目标、验收及实质性取舍；系统在授权范围内负责组织和修复工作。
Design 与 Implement 保留独立入口和阶段权限，但不再靠反复切换入口修复执行计划。

用户体验目标：

- 明确需求已有充分授权时，不为机械流程补问；确有未决事项时，先调查，再集中提出一轮有推荐方案的决策。
- 正常的上下文补充、任务拆分、验证准备和范围内修复，不要求返回 Design。
- Implement 遇到新实施选择时，在当前 change 内采用父模型推荐方案并记录，自动继续原执行，不要求用户再次选择、确认或传递版本号及收据。
- 同一失败不能通过 resume、回滚、换路由或重排任务无限续费。
- 不能自动解决的外部能力缺失与计算预算耗尽各有明确状态；二者都不伪装成设计决策。

“一轮”是正常旅程的验收目标，不是强迫系统在后来发现重大未知时保持沉默。

## 2. 代码证据与成因

### 2.1 用户授权绑定了精确执行计划

`src/delivery-compiler.ts` 的 `ReadyReceipt.approvals.gateB` 绑定计划批准，`PlanDraft` 又包含精确阶段路径、验证器、资源、依赖和跟踪信息。
`src/contracts.ts` 的 `PhaseBoundary`、`TaskBoundary` 把这些执行细节固定在任务上。
`src/submit-tool.ts:355` 的 `classifyCandidateContextRequest` 将任务之外的普通路径请求直接分类为 `approval-needed / boundary-review-needed`，即使只是读取遗漏的关联文件。
`prompts/abel-implement.md` 明确将这些等待引导至 `/abel-design --change`。

所以“没有写进本次任务”被当成了“用户没有授权”。
前一轮增加同任务跨阶段读取，只扩大了这一精确名单，没有改变判断模型。

### 2.2 计划兼容性判断过宽，容易重做无关工作

`src/workflow-policy.ts:1197` 的 `taskApprovalBoundary` 除去 tasks、outputs 和 tracking.taskIds 后，把剩余整个计划、完整任务及其输出一起比较。
`src/workflow-state-machine.ts:676` 的 `#admitDelivery` 用这个结果决定兼容任务。
例如全局 repair 参数变化，可能让没有输入或实现变化的任务也不再兼容。

现有 `src/durable-workflow.ts:1456` 的 `revalidateDelivery` 已能按输入内容、阶段事实及依赖闭包重建保留工作。
应继续使用这类证据判断，把授权有效性、调度修订和验证证据有效性分开。

### 2.3 恢复预算依赖内部可变身份

`src/workflow-policy.ts:538` 的 `recoveryKey` 包含完整任务、phase、路由及 `current_workspace_revision`。
`src/workflow-state-machine.ts:1530` 在 key 不相同时从零累计失败。
`src/durable-workflow.ts:1650` 的回滚通过创建新 revision 恢复内容。
`src/workspace-store.ts:98` 的 revision 哈希包含父 revision，因此内容恢复原样仍会得到新身份。

前一轮审计的临时测试使用真实 durable engine、候选应用和回滚路径，模拟持续拒绝的 Red 修正或 Green 验证。
首次操作产生 3 次候选请求，之后三次没有外部变化的 resume 分别使请求累计至 4、5、6；持久化 failures 每次仍为 1，未显示 exhausted，主工作区始终保留原内容。
该结果说明问题发生在真实恢复组合中；临时测试已删除，需要在实施时固化为永久回归测试。

直接把 key 改为整个工作区内容哈希也不充分：无关文件变化、任务重命名和候选来回摆动仍可能制造新上下文。

### 2.4 只投影第一个审批阻塞

`src/workflow-state-machine.ts:1717` 的 `#firstPaused` 与 `#statusByRun` 生成单个 `approval`。
tasks 列表没有逐任务审批分类和所需 Gate。
前一轮双任务临时测试中，T1 缺依赖授权、T2 缺行为授权，状态只展示 T1 的 Gate B，隐藏了 T2 的 Gate A+B。
这会让用户解决第一项后才看到下一项，形成串行追问。

### 2.5 提问和修复策略没有统一的运行时协议

`prompts/abel-design.md` 要求一轮集中决策，但也要求需求 ambiguous 时在探索前停下；运行时没有区分“必须由用户回答”和“可以调查的未知”。
`src/design-journal.ts:871` 起对自然语言 contract 做哈希，文本变化即可能成为 authorityChanged；引用变化已被修复，语义相同的重新表述仍可能导致失效。
`src/workflow-state-machine.ts` 与 `src/durable-workflow.ts:2683`、`:3398` 分别存在恢复计数或循环，恢复策略没有唯一所有者。
环境问题、归因不明、任务过大仍主要依赖父模型读提示后选择下一步。

## 3. 核心模型：契约 → 计划 → 执行能力

### 3.1 ChangeContract：稳定的用户授权

用结构化契约替换 WHAT 文本哈希加精确 HOW 审批的组合。
契约至少包含：

- `changeKey`：规范化仓库身份和稳定 change 身份；与会话、阶段激活、操作 ID 解耦。
- `revision`、`parentHash`、`contractHash`：不可变契约版本及变更来源。
- `acceptance`：稳定 Requirement/Scenario ID、已接受的预期结果、失败行为和必需的验证义务。
- `decisions`：稳定 decisionId、所选 optionId 或校验过的结构化值；展示说明与权威值分离。
- `authorityPolicy`：可读范围、可修改模块、保护区域、依赖策略、环境操作、验证规则、外部副作用限制和总资源预算。
- `approvalEvidence`：本任务既有授权或本次明确回答的来源绑定；不得由 Worker 生成。

契约中的验收定义一经接受便冻结；修改必须走明确的 amendment 操作。
不重新生成自然语言再通过哈希猜测是否还是原决定。
改写展示说明、增加来源引用、重排任务不修改契约。
确需修改自由文本验收定义时保守地作为显式变更处理，不宣称能用规范化算法证明任意自然语言等价。

私有数据库保存经校验的非敏感值、工件绑定和授权来源摘要，不保存原始对话、凭据或模型推理。
工件中的权威契约由控制层安装和校验，手工修改不能自行产生授权。

### 3.2 ExecutionPlan：机器维护的版本化方案

保留精确 DAG、阶段 read/write/delete、输出生产者、验证输入、资源锁和跟踪映射。
它们仍是硬约束，但属于一次计划，而非永久的用户审批名单。
计划绑定 `contractHash`，由编译器证明它在授权策略内且图结构、验证覆盖和输入输出闭合。

初版计划不必预测全部实现细节。
Implement 可以提交窄类型的修订：增加上下文、调整阶段路径、拆分任务、增加必要验证、声明允许的环境准备。
模型只能提出修订；控制层负责校验、安装新 revision 和失效处理。

### 3.3 AttemptCapability：每次执行的最小权限

控制层从当前契约、计划、任务、phase 和快照签发执行能力，绑定读写路径、验证器、资源及有效期/执行身份。
Worker 没有修改计划、批准决策或直接写主仓库的能力。
收到范围外请求时，先由策略层判断能否在 ChangeContract 内修订计划，再签发新的精确能力。
旧候选不能凭借新计划获得追认，必须重新校验并绑定有效能力。

这里的“模块范围授权”是父控制层的修订权限，不是把整个仓库暴露给每个 Worker。
路径仍经过组件级 no-symlink 检查，保护路径和外部状态根优先拒绝。

### 3.4 Gate B 改为系统就绪证明

取消用户对精确 ImplementPlan 的 Gate B 审批。
保留用户授权证明，以及代码生成的 `PlanCertificate`：绑定 contractHash、planHash、验证义务覆盖、输入输出闭包、策略版本和工具链约束。
Design 生成静态就绪证明；Implement 在准备环境后生成绑定实际内容及环境身份的执行就绪事实。
静态就绪不冒充运行环境已经可用。

契约不变时，计划修订只重新签发系统证明，无需再次询问用户。
外部消费者仍须校验证明、工件与私有授权事实，不能信任仓库里单独出现的 JSON。

## 4. 自主范围必须具体且可判定

Design 根据仓库事实生成一份有推荐默认值的范围说明，与产品取舍一起展示。
已存在明确的项目政策和同任务授权时直接复用，不机械补办确认。
不能仅因项目处于开发阶段就默认允许任意依赖、主机变更或外部副作用。

建议初始规则：

- 读取：允许控制层调查仓库普通源码、测试和项目配置中的关联路径；排除秘密、外部私有状态、Git 内部对象等保护区域。
  对子任务按需下发精确范围，并保留读取量限制。
- 普通代码和测试修改：在已接受模块范围内自动修订；新增关联辅助文件和可逆局部重构不需新决策。
  跨出已接受模块范围时先提出明确扩展，而非让模型声称“相关”即可越界。
- 依赖：复用现有依赖，以及按现有锁文件恢复依赖，按策略执行；新增运行时依赖或改变选型需要决策。
  新开发依赖仅在已接受的明确候选和版本规则内自动选择。
- 验证：新增覆盖、恢复已有 runner、使用已注册等价执行适配器可以自动处理；删除验收义务、降低断言、跳过失败测试或放宽成功条件不能作为修复策略。
- AGENTS：继续父控制层拥有；指定范围内的机械索引更新可预先授权，人写规则或其他政策变化需要明确决策。
- 环境：只执行受控适配器，限定包源、版本、目录、网络与 lifecycle script 政策；默认在私有环境操作。
  修改主机、获取秘密和扩大外部权限不属于普通修复。
- 主工作区：保留最终一次完整的 journaled apply、currentness 检查及 post-apply 验证；私有拆分执行不代表可以向用户工作区部分交付。

代码能严格判断这些结构约束，不能通用证明任意补丁都保持业务语义。
业务正确性仍由冻结的验收、Red/Green、影响验证及必要审查支持；发现与契约冲突或真正不确定的产品选择时进入决策协议。

## 5. Design：先收敛未知，再请求决定

未知项分成三类：

1. `discoverable`：仓库、依赖配置、既有约定可回答，继续调查。
2. `defaultable`：在已授权范围内有可逆且合理默认值，记录假设并推进。
3. `decision-required`：影响验收、重大取舍或超出权限，必须由用户决定。

只有第三类形成 `DecisionBatch`。
没有可识别的目标或存在多个无法区分的 change 时，仍可先问目标；普通实现细节不再被当作“需求 ambiguous”而阻止探索。
同一批给出完整的行为方案、实质性技术取舍、推荐默认值和自主处理范围。

决策项以稳定 decisionId、选项值和契约基线识别，记录 `open / answered / superseded`。
同一决定已有有效答案时拒绝重复创建待答项；答案变化必须明确替换原值。
追加问题必须引用新证据及其改变的具体决定，不允许因为编译器刚生成精确 DAG 再创建一个确认项。

运行时约束的是决策请求与等待状态，而不是靠问号数量判断对话质量。
现有 `src/index.ts` 主要控制输入、工具和提示激活，不能假设已能阻止父模型在普通文本里自行追问。
新增结构化决策呈现适配器统一发出 Abel 问题；父模型文本的额外追问通过宿主集成和真实对话评估验证，不能只靠提示正则宣称杜绝。

Design 保持不修改产品代码、不运行 Red/Green。
静态预检遇到允许自动准备的 runner 缺失时，生成有明确后置条件的准备动作；不为了让 Design 就绪而偷偷运行 shell 或安装环境。
缺少隔离基础设施等无法自举的能力应明确记录，不输出虚假的“可立即执行”。

## 6. Implement：当前 change 内闭环

### 6.1 等待类型分离

执行过程中保持 `running`，用 activity 投影 provisioning、diagnosing、replanning、verifying 等进度，不为每个动作增加一套独立运行状态机。
真正无法继续的等待分为：

- `awaiting-decision`：缺少产品或授权决定，携带整个待决批次。
- `awaiting-capability`：缺凭据、隔离能力或无法自动恢复的外部服务，携带可检测的恢复条件。
- `suspended`：自主预算耗尽、显式暂停或完整性问题，携带具体原因与保留证据。

取消、丢弃、拒绝与成功仍分别记录；等待与停止都不算完成。
存在阻塞时继续运行不依赖它的安全任务；全局决策变更影响的范围必须暂停，不能为了并行推进执行未经决定的分支。

### 6.2 汇总阻塞，支持当前任务内的增量决定

保存完整的 `BlockerSet`，每项包含稳定 ID、受影响任务/验收、类型、证据、已尝试动作、缺少的具体授权或能力、解决条件。
状态查询返回全部阻塞及关联关系，取代 `#firstPaused → approval` 单项投影。

询问前执行一次有界收集：汇总已知阻塞，允许正在进行的独立分析收敛，并对可静态发现的同类缺口做扫描。
不等待所有未来任务，也不为发现问题执行未授权工作；否则一个挂起任务就可能阻止任何提问。
已知问题归并为一批，依赖未来结果的问题在获得新证据后再追加，并解释差异。

新增封闭的决策路径 `request-decision → accept-decision`，由同一控制层处理 Design 初始决定和 Implement amendment，不暴露任意 put-state。
`accept-decision` 必须绑定 batchId、基线 contractHash、选项及宿主收到的用户回答来源；operationId 保证重放幂等。
批次过期或回答有歧义时不能套用到更新后的契约。
私有记录证明系统记录过授权，不冒充密码学人类身份验证。

控制层只发布被回答覆盖的增量契约，重新编译受影响计划、更新追踪投影并恢复原执行。
用户拒绝扩展时选择原授权范围内仍可满足验收的方案；不存在该方案则如实保留阻塞，不擅自缩减需求。

Implement amendment 不激活 `/abel-design`，也不获得 Design 的通用编辑能力。
其工件写入通过狭窄的 code-owned 发布事务完成，仅限被批准的契约增量和派生计划；手工任意修改现有规范不能通过此通道。
若用户自己希望全面重新讨论设计，仍可明确选择 `/abel-design`，并继续引用同一个 change。

### 6.3 单一恢复控制器

`workflow-state-machine.ts` 继续是唯一执行转换所有者。
把候选修正、任务 affected 修复、累计验证修复的策略选择和预算统一收进恢复控制器；执行服务一次完成一个有界动作并返回类型化证据，不再自己套一层修复循环。
路由 broker 保留连接层健康检查及有界 failover，向控制层报告实际消耗和终态，不能再次启动无限的外层换路由循环。

恢复动作只允许有限集合：

1. 补充上下文，或刷新受影响文件快照。
2. 根据具体失败证据修正候选或 Red 工件；修正 Red 必须重新证明所需失败再证明 Green。
3. 执行已允许的环境准备适配器，并验证能力后置条件。
4. 使用已配置的可用路由；不创建端点或索取新权限。
5. 对受影响验证做差分归因，再执行最小范围修复。
6. 修订计划或拆分任务，重新编译与校验证据。
7. 汇总真实决策缺口，等待外部能力，或在预算耗尽时暂停。

每个失败先检查已有事实与做过的动作，选取尚有证据价值的策略；不能只是把同一提示再次发送。
full-suite 归因不明时在预算内重放受影响测试、比较基线和候选，必要时在私有 revision 上有界隔离任务变更；仍不明确时保留失败及诊断，不自动标成 pre-existing。

环境准备必须能区分缺失安装与项目原有失败。
若准备动作改变验证工具链，应在同一工具链/overlay 下重建参考基线和候选验证，保存准备前诊断；不能先修掉产品或测试再把修复后的结果称为原始基线。

## 7. 用持久化事件阻止无进展循环

恢复身份采用系统创建的 `incidentId`，归属稳定的验收/验证义务与问题族，并记录关联任务及历史 fingerprint。
taskId、planRevision、routeId、workspaceRevision、operationId 只作为尝试上下文，不作为清空预算的开关。
分类不确定时关联到既有义务的恢复额度，不能通过产生新错误字符串获取新额度。

保留三层限制，配置随已接受策略固定：

- 动作去重：相同策略、相关输入内容、候选/诊断证据重复时不再次发起无价值尝试。
- incident 预算：持久化实际尝试、无进展连续次数、策略使用次数及总上限；新证据可允许另一种策略，但不归零累计消耗。
- change 预算：所有 incident、拆分任务、诊断和环境动作共享总执行次数、时间等资源上限，防止换问题名或重建任务绕过限制。

实施起点可采用每个 incident 最多 3 次无进展动作、最多 6 次恢复动作，change 最多 24 次恢复动作；这是待验收调优的初值，不是当前产品能力或已证明最优参数。
普通计划执行另有随任务规模计算并冻结的资源预算，拆分只是分配原有额度。

动作发起前，在持有租约的事务中保留 attemptId 和资源；结束后幂等写入结果并结算。
进程崩溃后先对账，已发起但结果未知的动作不能当成没执行重新免费发起。
排队和发起前取消不记失败；发起后取消不记业务失败，但已消耗的调用和运行时间仍计入总资源，不能用取消刷新成本上限。

“进展”必须有证据：满足新的冻结验收义务、在相同验证条件下通过此前失败的必需检查且保留既有通过项、或能力探测由不可用变为可用。
改了文件、换了模型、生成新哈希、新任务名称和内部回滚都不算进展。
无关检查通过不能关闭当前 incident；问题复发时保留关联历史与累计消耗。
在严格总预算下允许探索不单调的修复路径，无需把每一次失败都当成永远不可再试。

耗尽后，status 和 unchanged resume 不发起模型调用、不制造新问题，也不自动返回 Design。
新的有效外部证据可重新评估可行策略，但不能隐式扩大已耗尽总预算；确需额外资源时作为一次资源决定集中呈现。

## 8. 动态计划修订与证据保留

计划修订只在受影响任务的执行屏障处提交：停止签发旧能力，等待或取消相关尝试并完成结算，验证原契约和计划仍是当前版本。
无关任务可继续；发布采用租约和 compare-and-swap，冲突提案必须重新校验。

编译器必须重新证明：

- 所有原验收义务仍被覆盖，没有静默删除 Scenario 或弱化必需验证。
- DAG 无环，输出拥有唯一生产者，所有验证输入当前可用或由明确前驱产生。
- 拆分后的能力都在契约政策内，冲突路径和资源锁重新计算。
- 稳定验收 ID 与 lineage 映射保留，拆分/重命名不会创建全新的恢复预算。
- 阶段证据绑定验收定义、实际输入内容、测试/工具链、候选输出及正确的 Red/Green 顺序。

把“某个任务曾完成”和“当前义务有有效验证事实”分开。
调度顺序、展示文字或预算变更不使产品事实失效；读取内容、断言或适配器语义变化则重新验证相应闭包。
复用现有 revalidateDelivery 的逐路径比对与累积工作区重建机制，移除整个 planBoundary 的过宽比较。

拆分限制必须明确：

- 独立验收义务可以拆成各自完整的 Red/Green 单元。
- 一个不可拆验收需要多个实现片段时，只在私有准备分支暂存片段；它们没有独立 Green 完成资格，也不进入已验证累计工作区。
- 组合后统一运行对应 Green 和受影响验证，成功才提交该义务的完成事实。
- 有限片段、有限总字节、共享 incident 预算；无法在限制内完成则如实暂停。

因此需要引入“私有暂存片段”和“已验证候选”两种明确事实，不能简单让现有原子 candidate 接受半个补丁。
不可拆任务是第二阶段实现的显著复杂度，不能用 compact-patch 重试宣称已支持动态拆分。

计划及契约工件发布使用独立发布 journal：先持久化 prepared 记录和工件哈希，安装工件，最后发布证书/当前版本指针；读取方拒绝混合版本，重启后恢复或回滚未完成发布。
不声称文件系统 rename 与 SQLite 跨存储天然原子，也不复用产品 apply 状态冒充工件发布完成。

## 9. 模块及存储落点

保留现有 facade，不引入通用工作流平台或第二套调度器。
建议只增加四个内聚模块：

- `change-contract.ts`：授权、结构化决定、amendment 校验与策略判定的纯类型/函数；不启动 Worker。
- `change-journal.ts`：替换 Design 专用权威事实模型，存储契约版本、来源绑定、决策批次及发布事实；不拥有 Implement 转换。
- `recovery-controller.ts`：根据持久化 incident、预算和证据选择下一项有界动作；不直接写工作区或调用模型。
- `plan-revision.ts`：窄类型修订验证、兼容事实闭包和发布准备；由状态机提交。

现有模块的职责调整：

- `design-control.ts` 编排调查、初始决策和静态交付；`delivery-compiler.ts`、`implement-graph.ts` 校验所有初版及修订版计划。
- `workflow-state-machine.ts` 调用上述模块，统一决定执行、恢复、决策等待、计划切换和完成；`durable-workflow.ts` 只执行被指定的有界工作区/验证动作。
- `submit-tool.ts` 返回类型化资源需求和失败证据，不把 Worker 的“需要审批”直接变成阶段路由；`scoped-tools.ts` 等继续强制执行精确能力。
- `control-contracts.ts` 增加封闭决策协议，status 返回 blockers、decisionBatch 和自动恢复摘要；resume 从私有当前证明发现继续条件，不向用户暴露 receipt 配对操作。
- `src/index.ts` 接入可信用户输入来源、统一决策呈现及阶段工具限制；四个公开 slash 入口保持显式激活。
- `subagent-activity.ts` 展示正在自动处理的原因、必要等待和保留进度；取消/暂停不能显示完成。

继续使用 owner-private SQLite 和现有租约，不为每个模块再创建一个数据库。
存储新增或替换以下规范化事实：contracts、decision_batches/items、plan_revisions、blockers、recovery_incidents/attempts、resource_reservations、artifact_publications。
关键计数、状态、唯一键和关联使用 checked schema/约束，不能只塞进 `attempt_diagnostic_json`。
诊断与 TUI 是这些事实的脱敏投影，不承担恢复授权或预算权威。

保留 `artifact-store`、`workspace-store`、`task-ledger`、Bubblewrap、`safe-path`、候选 sealing、`apply-transaction`、broker 及子会话生命周期。
新增模块仍遵守现有无循环依赖与 child 不引用 apply/run authority 的架构测试。

## 10. 开发阶段的实施顺序

先形成一份替代旧授权/恢复模型的 OpenSpec change，再按以下纵向切片实施，每个切片先写有行为意义的失败测试。
本文本身不是已完成或已校验的 OpenSpec delivery。

1. 固化已复现的反例与指标：内部回滚反复续费、双审批只展示第一项、关联读路径触发 Gate、全局计划元数据导致无关任务失效。
2. 替换契约和交付模型：一个稳定授权契约、系统 PlanCertificate、初始 DecisionBatch；同步 Design 提示与生产装配，移除人类 Gate B。
3. 打通最小自主闭环：范围内读写计划修订、全部阻塞投影、Implement 内增量决定、受影响事实重验及发布恢复。
4. 收敛恢复控制权：独立持久化 incident 和资源账本，移除 durable-workflow 的嵌套策略循环；覆盖重启、并发、取消与路由切换。
5. 完整自动解决能力：环境准备、失败归因、独立任务拆分，再实现不可拆义务的私有片段组合；每类动作都有真实生产装配测试。
6. 同步 prompts、README、AGENTS、现行 specs、包成员清单和 traceability；运行完整验证及真实环境旅程。

没有历史包袱，因此采用单一新 schema/协议，不保留旧 Gate B、旧恢复诊断读法或双版本分类器。
开发切换使用新的私有状态版本目录；不自动删除旧数据库、候选和用户工作区。
若旧版本有未结算 apply，必须先由旧实现恢复到稳定状态，禁止新实现直接接管半次事务；稳定旧状态可以只读保留，不要求实现通用迁移器。
这是开发切换策略，不应成为最终用户每次工作流需要经历的确认步骤。

## 11. 可验证的完成标准

### 确定性契约测试

- 明确目标、有既有授权：0 次新增审批请求；确有未决初始选择：1 个集中 DecisionBatch。
- 重启、刷新、重复编译、展示文字变化：相同决定不重新进入待答。
- 未列出的关联只读文件、范围内辅助文件：内部计划修订成功，用户决策次数和 Design 返回次数均为 0。
- 新依赖和行为缺口同时被发现：一次 status 返回两项，一次回答覆盖同一批，保留无关任务；不能只测 firstPaused。
- 新证据需要实质性改变：批次说明具体增量；未经回答不发布权限扩大的契约。
- 真正缺外部凭据：awaiting-capability，不循环问、不启动 Design；能力恢复后按证据继续。
- 失败 → 回滚 → 同样失败，反复 resume/reopen：总尝试有上限，不因 revision 链增长而重置。
- 切路由、改任务 ID、拆分、错误字符串变化及候选 A/B 振荡：不能重置 incident/change 总额度。
- 取消、进程退出、租约接管发生于保留/启动/结算任意位置：资源不会重复扣算或免费重试，不留活动子进程。
- 计划发布中断：只见完整旧版或完整新版，错误绑定候选被拒绝；重放幂等。
- Red 工件修改、验证输入变化、任务拆分：失效范围正确，冻结验收不被削弱，累计验证通过后才允许完整 apply。

### 真实执行与交互验收

在 Linux Bubblewrap 路径覆盖 Red/Green、依赖恢复、范围内扩展、拆分、重启及最终主工作区边界；多平台继续验证已有 OpenSpec/包合约，不扩展宣称 native isolation 的平台范围。
在完整 Design → Implement 宿主装配中记录实际父模型可见的提问与用户输入，检查是否出现无 DecisionBatch 的额外确认。
确定性测试验证协议不重复提问，少量固定场景的真实模型评估验证措辞与交互行为；后者不能替代硬约束测试。

新增本地脱敏指标：`decisionBatchCount`、`duplicateDecisionRequestCount`、`stageReturnCount`、`autonomousRecoveryCount`、`recoveryExhaustedCount`、`modelLaunchCount`、`invalidatedEvidenceCount`。
“不回 Design”必须与真实验收完成、有限资源和无需重复提问同时成立，不能把所有失败改名为 paused 就算达成。
不默认上传遥测，也不记录问题原文或秘密。

实施完成时运行 `bun run verify`、`bun run traceability:check`、`bun run check:agents`、新 change 的严格 OpenSpec 校验及上述新增旅程。
现有 648 项通过记录属于上一轮局部改动，不能用来证明本文所提协议已经实现。
