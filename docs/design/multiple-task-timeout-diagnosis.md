# 多任务 10 分钟截止原因排查

最近一次 `gpt/gpt-6-astra` 多任务评估耗尽了整轮预算，截止时还未提交计划。
本次记录不支持“计划校验计算慢”或“多任务执行调度慢”的判断：两者都尚未运行。
主要时间花在父模型多次响应的等待与生成，工具调用的串行组织放大了每轮时延。

## 历史运行的时间分解

根据同次运行的工具起止与 HTTP 元数据，27 个工具调用完全串行。
原始评估结果见 [redesigned-multiple-tasks.json](redesigned-multiple-tasks.json)。

| 时间归属                             | 耗时       | 占 600 秒比例 |
| ------------------------------------ | ---------- | ------------- |
| 本地读取、搜索与 Design 控制调用     | 0.350 秒   | 0.06%         |
| 一次调查子调用，内部两次请求         | 20.015 秒  | 3.34%         |
| 父模型响应等待、生成、传输与宿主处理 | 579.635 秒 | 96.61%        |

27 个已收到响应头的请求等待响应头累计 363.512 秒，中位数 12.323 秒，最大 30.845 秒。
这部分已经包含在最后一行，不能再次加到总耗时上。
响应头之前的时间无法进一步区分网络、代理排队、服务端计算或缓冲；HTTP 200 也不保证流式正文最终成功。
因此可以定位慢发生在哪个边界，尚不能确定 Provider 内部哪个环节慢。

| 运行区间   | 所做工作                        | 区间耗时  |
| ---------- | ------------------------------- | --------- |
| 0–200 秒   | 初步调查，连续读取与搜索        | 约 200 秒 |
| 200–362 秒 | 两项决策、Gate A 修正、绑定变更 | 约 163 秒 |
| 362–422 秒 | 生成调查请求并等待子调用        | 约 60 秒  |
| 422–560 秒 | 分四次写入设计产物              | 约 138 秒 |
| 560–600 秒 | 再查编译器源码，随后被截止取消  | 约 40 秒  |

唯一的工具格式错误发生在 Gate A，模型修正后重发花了约 42.7 秒；错误校验本身只花了毫秒。
历史观测只保存安全错误码，未保存请求结构，不能追溯断言该次具体哪个合同字段填错。
该运行没有提交 `plan-draft.json`，没有调用预检、编译或最终交付，也没有进入 Implement。
因此这次运行尚未实际检验草稿字段自动推导的模型端收益。

600,000 ms 来自 `scripts/evaluate-workflow.mjs` 的整轮计时器，覆盖 Design、父会话结束、Implement 和独立验收。
它不是 SDK 单请求超时，也不是多任务调度器的执行上限。

## 子调用连接超时的独立复现

`src/worker-broker.ts` 在 attempt 开始时启动 10 秒 `connect-timeout`，直到 `onHeaders()` 或流进展才清除。
`src/packet-runtime.ts` 把 Provider 的 `onResponse` 绑定到 `onHeaders()`；`src/parent-provider.ts` 在 SDK 收到 HTTP Response 后触发它。
这个边界没有实际 TCP/TLS 已连接的观测，因此响应头前的服务端等待也被算作“连接”。

使用真实本地 HTTP 服务、原有 WorkerBroker 和两组延迟进行复现，没有调用模型或修改超时常量：

- TCP 约 18 ms 已连接，服务端约 23 ms 收到请求，但响应头延迟 11 秒：两次请求都被 10 秒计时器取消，约 20.019 秒后返回 `connect-timeout`。
- 响应头立即返回，正文延迟 11 秒：一次成功，约 11.014 秒完成。

这证明超时分类与实际连接状态不一致，延迟响应头的可用服务也会被提前取消。
历史父请求有 17/27 次等待响应头超过 10 秒，说明该策略与当时观测的响应时延不匹配。
历史子调用的两次请求分别约 9.980 秒、9.982 秒后被取消，与这条路径一致；但当时没有保留子调用失败码，不能把推断写成已确认的历史根因。
即使完全省掉该子调用的 20 秒，历史运行仍会有约 580 秒其他耗时，不能靠修正它单独解决整轮截止问题。

## 优化顺序

1. 优先减少模型的串行轮数：合并独立读取，用已取得的少量仓库证据直接做简单设计，只为尚未解决的独立问题启动调查子调用。
2. 保留草稿字段推导和精准反馈，减少进入计划构造后的返工；它们不覆盖这次发生在计划提交前的主要耗时。
3. 将子调用的连接观测与等待响应语义对齐；当前不能把响应头延迟诊断成 TCP 连接失败。
   需要按可观测事件设计预算，保留取消、有限重试和总时限。
4. 分别报告 Design、阶段交接与 Implement 的时间和完成状态。
   延长整轮预算可以作为独立的容量实验，不能替代上述定位，也不能冒充相同条件下的提速。

## LocalModel 相同场景复测

按用户当前配置使用 `abel/LocalModel`，保留 `xhigh`、相同需求和独立验收，以及 600,000 ms 上限。
未修改全局 Provider 配置，也未向运行中的模型注入修正。
结果仍为 `evaluation-deadline`，截止时 Gate A 尚未通过，没有提交计划或启动 Implement。

| 观测项                     | 上一轮 gpt-6-astra    | 本次 LocalModel      |
| -------------------------- | --------------------- | -------------------- |
| 工具调用 / 失败            | 27 / 1                | 40 / 3               |
| 父模型请求数               | 28                    | 23                   |
| 父请求等待响应头中位数     | 12.323 秒             | 1.402 秒             |
| 已观测父请求等待响应头合计 | 363.512 秒，27 个响应 | 34.229 秒，23 个响应 |
| 父模型响应、生成与宿主处理 | 579.635 秒            | 461.061 秒           |
| 调查子调用占用的实际时间   | 20.015 秒             | 138.681 秒           |
| 本地工具执行的独占时间     | 0.350 秒              | 0.258 秒             |
| 计划提交 / 计划预检        | 均未发生              | 均未发生             |

LocalModel 的并行工具以时间区间并集计算，避免重复计时。
这些是两次被截止截断的实际工作轨迹，不是完成同等工作量的速度基准。
本次虽然合并了部分读取，仍进行了 14 次 `ls`、11 次 `read`、4 次 `find` 和 2 次 `grep`。
两个成功的调查子调用分别约 95.162 秒和 43.519 秒；另一个并行调查请求立即发生工具错误，随后才成功重发。

父模型已经完成的流式响应累计 417.075 秒；最长一轮约 129.184 秒，报告输出 8,302 tokens，结束后仅执行了一次 `record-decision`。
该轮在第 517 秒结束，随后第 553 秒 Gate A 请求发生格式错误，模型转去查阅合同源码，最后被截止取消。
这说明本次的直接问题是长生成轮次、调查与构造步骤过多；降低推理强度是否能保留质量并改善耗时，还需要另行对照，不能仅凭 `xhigh` 配置断言。

三个工具错误分别发生在初次 `start`、一个调查请求和 Gate A。
Gate A 的观察已确认是 `gate-a`、对象合同、无缺失顶层字段和额外顶层字段，但未保留合同正文或所有值校验结果，仍不能精确断言哪个值无效。
工具通用的 `invalid-design-control-request` 反馈也没有指出具体字段，增加了模型回查规范的成本。

29 个 Provider 请求均收到 HTTP 200；宿主模型错误和自动重试均为 0。
唯一 HTTP 请求错误发生在第 599.964 秒，紧邻整轮截止和 assistant `aborted`，不记为 SDK `Request timed out`。
本次两个成功调查调用也未复现历史的响应头前取消；本地实验发现的 10 秒计时语义问题仍独立存在。

因此应先优化简单需求的调查与构造轮数，并让 Gate A 等入口返回具体字段诊断；不应把此次失败归因于编译性能、Red/Green 测试耗时或多任务合并。
源码查阅不只可能发生在计划校验失败之后，计划提交前也会产生构造成本。
